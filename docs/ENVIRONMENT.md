# Environment variables

Every environment variable Innogram reads, which service reads it, whether it is required, its default and what it does. The tables are checked against the code (`apps/auth_microservice/src/config/env.ts`, the `AppConfigService` and `env.validation.ts` of core and notifications, `apps/client_app/next.config.ts`), the compose files and the Dockerfiles. The two templates are [`.env.example`](../.env.example) (local development) and [`.env.production.example`](../.env.production.example) (container stack). Every variable in either file is listed below.

## How configuration is loaded

- **One root `.env`** (gitignored; `cp .env.example .env`). Auth (`dotenv` in `config/env.ts`), core and notifications (`@nestjs/config`), the TypeORM `data-source.ts` files, the seed scripts and the client's `next.config.ts` all read it. Each service has its own port variable, never a shared `PORT`.
- **Containers** read `.env.production` instead (`env_file` for auth, core, notifications and their migrate jobs, plus `--env-file .env.production` for the interpolation in `docker-compose.yml`). See [DEPLOYMENT.md](DEPLOYMENT.md).
- **An empty value counts as unset**, so `S3_PUBLIC_ENDPOINT=` falls back to its default.
- **Fail fast.** Core and notifications validate their environment at bootstrap (`src/config/env.validation.ts`) and exit with one error that names every failing variable, never its value. Auth throws on the first missing required variable (`Missing required enviroment variable: <KEY>`, spelling as in the code).
- **Business code never reads `process.env`.** Core and notifications go through `AppConfigService`, auth through `config/env.ts`. Exceptions: `LOG_LEVEL` (read by `@repo/shared`'s logger), `NOTIFICATIONS_RELAY_QUEUE` (read by core's relay consumer) and the client's `next.config.ts`.

Legend for the tables. **Required** names the services that refuse to start without the variable, `no` means optional. A default of `-` means "none, the feature is off or the value is empty".

### Client build (Next.js)

The client has no runtime configuration. `next.config.ts` reads the variables below at **build time** and inlines them as `NEXT_PUBLIC_AUTH_SERVICE_URL`, `NEXT_PUBLIC_CORE_SERVICE_URL`, `NEXT_PUBLIC_NOTIFICATIONS_SERVICE_URL`, `NEXT_PUBLIC_CLIENT_PORT` and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (read in `src/lib/config.ts`). Do not set `NEXT_PUBLIC_*` yourself. Only browser-safe values are exposed, never a backend secret.

| Variable                                                            | Service(s)        | Required         | Default                                          | Description                                                                                                                           |
| ------------------------------------------------------------------- | ----------------- | ---------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_SERVICE_URL`, `CORE_SERVICE_URL`, `NOTIFICATIONS_SERVICE_URL` | client            | production build | `http://localhost:3002` / `3001` / `3003` in dev | See the URL table above. A `NODE_ENV=production` build **throws** when one is missing; a dev build warns and falls back to localhost. |
| `CLIENT_PORT`, `GOOGLE_CLIENT_ID`                                   | client            | no               | `3000` / empty                                   | See above.                                                                                                                            |
| `CLIENT_PUBLIC_AUTH_URL`                                            | compose build arg | no               | `http://localhost:3002`                          | Compose-only name: `docker-compose.apps.yml` passes it to the client image as the `AUTH_SERVICE_URL` build arg.                       |
| `CLIENT_PUBLIC_CORE_URL`                                            | compose build arg | no               | `http://localhost:3001`                          | Passed as the `CORE_SERVICE_URL` build arg.                                                                                           |
| `CLIENT_PUBLIC_NOTIFICATIONS_URL`                                   | compose build arg | no               | `http://localhost:3003`                          | Passed as the `NOTIFICATIONS_SERVICE_URL` build arg.                                                                                  |

Docker build args `NODE_IMAGE` (default `node:20-alpine`) and `TURBO_VERSION` (default `1.13.4`) only pin the base image and the `turbo prune` version in the four Dockerfiles; they are not environment variables.

The `CLIENT_PUBLIC_*` values must be reachable from the user's browser (published host ports or public hostnames, never container names). The published client image only works for the compose default URLs; any other environment rebuilds it with its own values.

## Dev vs production vs test

| Aspect                 | Development (`.env`)                                                                | Production-style containers (`.env.production`)                                                                                               | Tests                             |
| ---------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Template               | `.env.example`                                                                      | `.env.production.example`                                                                                                                     | Reuses the root `.env`; see below |
| `NODE_ENV`             | `development`                                                                       | `production`                                                                                                                                  | `test` where a suite sets it      |
| Hostnames              | `localhost` and the published infra ports (Redis cache `6380`, S3 `9000`)           | Compose service names (`postgres`, `redis`, `redis-cache`, `rabbitmq`, `seaweedfs`, `mailpit`) and in-network ports (cache `6379`, S3 `8333`) | Same as development               |
| Secrets                | Placeholders are accepted by auth outside production; `REDIS_PASSWORD` may be empty | `CHANGE_ME` is rejected in every secret, `REDIS_PASSWORD` is required, auth also demands 32+ characters for the JWT secrets                   | Placeholders                      |
| Swagger                | On by default                                                                       | Off by default; set `SWAGGER_ENABLED=true` to expose it                                                                                       | On                                |
| Log level              | `debug`                                                                             | `info`                                                                                                                                        | per `LOG_LEVEL`                   |
| Cookie                 | `SameSite=strict`, not `Secure`                                                     | `SameSite=strict` unless `AUTH_COOKIE_SAMESITE` is set, always `Secure`                                                                       | n/a                               |
| `PERF_INSTRUMENTATION` | may be `true` for perf work                                                         | must stay `false` (core refuses to start otherwise)                                                                                           | may be `true`                     |
| `S3_PUBLIC_ENDPOINT`   | usually empty                                                                       | set to the browser-facing URL (`http://localhost:9000` by default)                                                                            | empty                             |
| Client URLs            | read from `.env` by `next dev`                                                      | baked into the image through the `CLIENT_PUBLIC_*` build args                                                                                 | n/a                               |

**Tests.** Core's and notifications' `test/setup-env.ts` (unit and e2e) load the root `.env` without overriding the process environment, then fill only the still-unset required variables with throwaway placeholders (`JWT_SECRET`, `INTERNAL_API_TOKEN`, S3 and RabbitMQ values). Running the e2e suites needs the dev stack (`npm run docker:up`), so the real infra values come from `.env`. Specs may also set `NOTIFICATIONS_RELAY_QUEUE` to isolate the relay queue. Some core e2e specs fall back to a `JWT_ACCESS_SECRET` variable before `JWT_SECRET`; no service reads it, so it is not part of the configuration.

**CI** (`.github/workflows/ci.yml`) sets only `AUTH_SERVICE_URL`, `CORE_SERVICE_URL` and `NOTIFICATIONS_SERVICE_URL` for the production client build; unit tests need no environment.

## Secret handling

- **Never commit real values.** `.env` and `.env.production` are gitignored; the two `*.example` files hold placeholders only. Do not paste secrets into issues, logs or CI output.
- **Generate production secrets randomly**, for example `openssl rand -hex 32` (64 hex characters) for `JWT_SECRET`, `JWT_REFRESH_SECRET` and `INTERNAL_API_TOKEN`. Use a different value for each. Replace every `CHANGE_ME` in `.env.production` (database, Redis, RabbitMQ, S3 and Grafana passwords too). In production, auth and the Nest services refuse to start while any secret they read still contains `CHANGE_ME`, and Grafana refuses it in `GRAFANA_ADMIN_PASSWORD`.
- **Keep `INTERNAL_API_TOKEN` identical** in auth, core and notifications, and never expose it to the browser. Auth's internal listener (port 3012) is never published or proxied.
- **Rotating** `JWT_SECRET` or `JWT_REFRESH_SECRET` invalidates all issued tokens and sessions; rotating `INTERNAL_API_TOKEN` needs a coordinated restart of all three backends (and Prometheus). Rotating the Postgres, RabbitMQ or S3 credentials in `.env.production` does not change what the existing volumes already hold, so change them in the running service first.
- **The client has no secrets.** Everything baked into the client image is public (URLs, the Google client ID). The client container has no `env_file`.
- **Logs never contain secrets.** Validation errors name the variable and the rule, never the value.
- **The `.env.example` JWT placeholders are special**: auth compares against them (`JWT_PLACEHOLDER_SECRETS` in `config/env.ts`), so keep those two lines byte-identical to the code.
- **Real SMTP and Google credentials** belong only in `.env` or `.env.production`; Mailpit needs none.
